# App, frame loop
Part of: app
Read when: you change the frame loop: ticks, keys, draw order, the catch-up cap.

## Interface

### game/app/loop.py (Integration Engineer)
```python
async def run() -> None:
    ...
    # Startup order, then guarded(functools.partial(start, choice.mode), choice.mode).


async def start(mode: RunMode) -> None:
    ...
    # The guarded body. Imports app.frame here, inside the guard, then awaits frame_loop(mode).
```
Module level: stdlib, `app.mode`, `app.log` and `app.guard` only. No pygame, no `core`, no `ui`, no `app.frame`.

### game/app/frame.py (Integration Engineer)
```python
ARROW_NAMES: dict[
    int, str
]  # pygame.K_UP -> "up", K_DOWN -> "down", K_LEFT -> "left", K_RIGHT -> "right"


async def frame_loop(mode: RunMode) -> None:
    ...
    # pygame init, window, frames until pygame.QUIT.
    # Owns: flow (core.game_flow.GameFlow, from DRA-125; it holds the run), thrust (core.ship.Thrust),
    # confirm and focus_lost_pending (bool, DRA-125), overlay_visible (bool).
```
Imports pygame, `app.settings`, `app.mode`, `app.tuning` and `app.debug_spawns` (DRA-29), `core.world`, `core.ship` (for `Thrust`), `core.run`, `ui.look`, `ui.starfield`, `ui.drifters.registry` (DRA-29, for `render_drifter`), `ui.ship_view`, `ui.debug_overlay`, `ui.game_over` and `ui.hud`. From DRA-23 it no longer imports `core.scroll`, `spawn` or `step`. From DRA-76 it also imports `random` (stdlib), `app.waves`, `core.waves` (for `start_waves`) and `draw_debug_wave_lines` from `ui.debug_overlay`. From DRA-117 it also imports `load_graze_rules` from `app.tuning` and `draw_graze_ring` from `ui.graze_view`. From DRA-125 it also imports `load_last_life_rules` from `app.tuning`, `core.game_flow` (`GameFlow`, `Screen`, `TickInput`, `start_flow`, `step_flow`, `add_flow_drifters`), `draw_burst` from `ui.burst_view`, `draw_menu` from `ui.menu`, `draw_instructions` from `ui.instructions`, `draw_leaderboard` from `ui.leaderboard` (and, from the credits page, `draw_credits` from `ui.credits`), `draw_pause_box` from `ui.pause_box` and `draw_game_over_choices` from `ui.game_over`; it no longer calls `step_run` or `add_drifters` itself. From DRA-126 it also imports `load_saves` and `write_saves` from `app.saves`, `stop_saves` from `core.game_flow` and `draw_name_picker` from `ui.game_over`. From DRA-159 it also imports `MuteIconView` from `ui.mute_icon`, `load_mute_icon_look` from `app.mute_icon_tuning` and `load_mute_icon` from `app.assets`. It reads `pygame.K_m`. `_draw` gains two trailing arguments with defaults, `mute_icon_view: MuteIconView | None = None` and `music_muted: bool = False`, so a caller that passes neither (the window-view test) draws exactly as before (Rules, The mute icon).

## Rules

Frame loop (`app/frame.py`, `frame_loop(mode)`):
- Inside the guard: `pygame.init()`, then the window opens from the HUD rules (HUD-PANEL): `hud_rules = load_hud_rules()` first, then `window = pygame.display.set_mode((hud_rules.window.width, hud_rules.window.height))`, 856 × 518. `field = window.subsurface(pygame.Rect(hud_rules.window.field_x, hud_rules.window.field_y, SCREEN_W, SCREEN_H))` is the play area (`SCREEN_W`, `SCREEN_H` from `core.world`, unchanged). The HUD art loads after the display opens: `hud = HudView(hud_rules, load_hud_art(hud_rules))`, and a `WindowBackdrop`. A bad or missing `hud.json`, picture or font raises inside the guard like every other file. Source: 03-world-and-camera.md, window_w, window_h, play_area; systems/hud.md; systems/world.md.
- Before the first frame (DRA-29): `tuning = load_tuning()`, in both modes, before `start_run()`. A bad or missing tuning file raises inside the guard, so the page shows the error screen and the log holds the file and field. Source: game/CONTEXT.md, Error handling (validate at the edge); 15-tech-constraints.md, rule 8; scope report DRA-29, Limits ("The app loads and validates them once at startup").
- Before the first frame, debug mode only (DRA-39): `spawn_list = load_debug_spawns(tuning)`, right after `load_tuning()`. A bad or missing list raises inside the guard the same way. Normal mode never reads the file, so a broken list can't break normal play. Source: 15-tech-constraints.md, rule 7 (debug only adds the test spawn list); scope report DRA-39, Limits.
- Before the first frame, both modes (DRA-76): `book = load_wave_book(tuning)`, right after `load_tuning()` and before the spawn list. A bad or missing wave file raises inside the guard, so the page shows the error screen and the log names the file and the problem, in both modes, whatever debug mode plays. Source: scope report DRA-76, Limits ("Loading the wave and playlist files once at startup, in both modes"); 15-tech-constraints.md, rule 8.
- Before the first frame, both modes (DRA-117): `graze_rules = load_graze_rules()`, right after `load_tuning()`. A bad or missing `scoring.json` raises inside the guard, so the page shows the error screen and the log names the file and the field. The run is started with it: `start_run(waves=..., graze_rules=graze_rules)`, below. A retry keeps it inside core (`systems/run.md`, a game-over tick). Source: scope report DRA-117, Limits ("Every value in tuning"); 15-tech-constraints.md, rule 8.
- Before the first frame (DRA-76): `plays_list` is True only in debug mode with the spawn list's `play` equal to `PLAY_LIST` (its default). The run is `start_run(waves=None, graze_rules=graze_rules)` when `plays_list`, else `start_run(waves=start_waves(book, random.getrandbits(64)), graze_rules=graze_rules)` (`graze_rules` from DRA-117): one seed from Python's `random` module, which the interpreter seeds from the OS at start, drawn once per page load. Core makes every later run's seed from it (`systems/waves.md`, Seeds). The app never draws another seed and never restarts the waves. Source: 10-ui.md, rule 7; 09-waves.md, rule 4 (picks new every run); scope report DRA-76, Not in GDD (picks not seeded, new every run).
- Before the first frame, both modes (DRA-125): `last_life_rules = load_last_life_rules()`, right after `load_graze_rules()`. A bad or missing `last_life.json` raises inside the guard, so the page shows the error screen and the log names the file and the field. The first run is started with it, `start_run(waves=..., graze_rules=graze_rules, last_life_rules=last_life_rules)`, and wrapped once: `flow = start_flow(run)`. The first frame shows the menu. Source: scope report DRA-125, Limits ("Every value in tuning, never hard-coded: `last_life_delay` ..."); 02-game-flow.md, rules 1 and 2; 15-tech-constraints.md, rule 8.
- Before the first frame, both modes (DRA-126): `saves = load_saves()`, right after `load_last_life_rules()`, then `flow = start_flow(run, saves)`. `load_saves` never raises for a storage or data problem: saves that don't work give None and the game starts as usual (`save-storage.md`). The saves are never read again. Source: 11-save-data.md, rule 5; 91-decision-log.md, row 93 (debug saves the same).
- Before the first frame: `overlay_visible = mode is RunMode.DEBUG`. From DRA-125 play starts when Play is picked on the menu: the ship first appears at screen center on the first frame drawn after that tick. Source: 03-world-and-camera.md, ship_start; 10-ui.md, debug_overlay_toggle (shown from the first frame); scope report DRA-13, Values needed (play start); systems/game-flow.md, Rules, MENU.
- The app never calls `spawn`, `step`, `start_scroll`, `step_scroll`, `start_run` (after the first), `step_run`, `next_run` or `add_drifters` itself. A respawn, the wait, the last life, game over, the pause, the screens and a new run all happen inside `step_flow`. Source: systems/run.md; systems/game-flow.md.
- **Screens.** On every screen the frame loop carries on as always: it reads events, builds `thrust` and `confirm`, runs ticks (`step_flow` decides what they do) and draws. Nothing in the app depends on the screen but the draw. Source: systems/game-flow.md, Rules.
- Each frame, in order: read all events, build `thrust` and `confirm` from the held keys, add the frame time to the accumulator, run one tick per whole 1/60 s in the accumulator, draw, `pygame.display.flip()`, `await asyncio.sleep(0)`. Source: 15-tech-constraints.md, rules 1 and 2.
- Frame time comes from a monotonic clock (`time.perf_counter`). Ticks never use frame time. Source: 15-tech-constraints.md, rule 2.
- **Held keys.** After the events, read `pygame.key.get_pressed()` once and build `Thrust(up=pressed[K_UP], down=pressed[K_DOWN], left=pressed[K_LEFT], right=pressed[K_RIGHT])`. Every tick in that frame uses the same `thrust`. Only the four arrow keys move the ship. Source: 01-vision.md, locked decision 1; 04-ship.md, rule 2.1.
- **Confirm keys** (DRA-125). From the same `get_pressed()`: `confirm` is True when any key in `CONFIRM_NAMES` is held (Enter, keypad Enter or Space). Every tick in that frame uses the same `confirm`. The app never works out a fresh press: `step_flow` does, from the held state tick by tick. Source: 02-game-flow.md, confirm_keys (locked), fresh_press; 01-vision.md, locked decision 1.
- **Focus** (DRA-125). An event in `FOCUS_LOST_EVENTS` (the window or the browser tab losing focus, being hidden or minimized) sets `focus_lost_pending = True`. The next tick gets `TickInput(focus_lost=True)`, then the flag is cleared, so each loss reaches exactly one tick even when its frame runs none. Getting the focus back sets nothing. The browser check must show which of these events pygbag delivers for a tab switch and a click outside the page; if none arrives for either, stop and report it: that is a contract change, not a fix. Source: 02-game-flow.md, pause_on_focus_loss (locked), rule 7; 91-decision-log.md, row 81.
- **Tick.** `flow = step_flow(flow, TickInput(thrust=thrust, confirm=confirm, focus_lost=focus_lost_pending))`, then `focus_lost_pending = False`. One `step_flow` call per tick. Right after it, every tick: `flow = add_flow_drifters(flow, due, tuning)`, where `due` is `debug_spawns_due(spawn_list, flow.run.scroll.ticks)` when `plays_list`, else `flow.run.wave_spawns_due` (DRA-76). Never both. `add_flow_drifters` adds them only after a tick the run was stepped, so a paused run, a page and the game-over screen get nothing (DRA-125). Then, every tick (DRA-126): if `flow.saves_changed` and `flow.saves` is not None, `write_saves(flow.saves)`; when it returns False, `flow = stop_saves(flow)`. So each saved entry is written right after its tick, even when one frame runs several ticks, and never twice. The app never builds a drifter itself, never changes `flow.run.drifters` and never reads a wave. It never builds, changes or orders a save entry: core does (`systems/saves.md`). Source: 04-ship.md, rule 1; systems/game-flow.md, `add_flow_drifters`; 15-tech-constraints.md, rules 2 and 7; systems/run.md; scope report DRA-76, Limits ("Debug mode: ... the normal waves or the test spawn list").
- **Draw** (from DRA-125 by `flow.screen`; `run` is `flow.run`). On MENU, INSTRUCTIONS, LEADERBOARD and CREDITS (HUD-PANEL; CREDITS from the credits page, 2026-11-08): `backdrop.draw(window, background, background_ticks)`, then `draw_menu(window, look, flow.menu_selection)`, `draw_instructions(window, look)`, `draw_leaderboard(window, look, flow.leaderboard)` (DRA-126) or `draw_credits(window, look)` (the `look` argument is DRA-147: one `ScreenLook` built at startup from `tuning/screens.json`, `systems/screens.md`), all on the whole window; nothing else on those four: no world, no overlay, no HUD, no frame. On the other screens the background and the list below draw on `field`, the play-area subsurface, so every coordinate stays a play-area coordinate. On PLAYING, PAUSED and GAME_OVER, the list below, with three DRA-125 additions: `draw_burst(surface, run.burst)` only if `run.last_life`, right after the ship's place; after the list and the HUD (HUD-PANEL), and after the mute icon of DRA-159 (see The mute icon): on PAUSED, `hud.dim(window)` then `draw_pause_box(window, look)`; on GAME_OVER (not on `run.game_over`), `hud.dim(window)` then the game-over calls of `systems/game-flow.md`, Presentation (`flow.screen` GAME_OVER row, DRA-126), all on `window`: `draw_game_over(window, look, flow.game_over_message, picker_shown)`, `draw_final_score(window, look, run.score, picker_shown)`, `draw_name_picker(window, look, flow.picker, flow.picking)` only when `flow.picker` is not None, then `draw_game_over_choices(window, look, flow.game_over_selection, picker_shown, active=not flow.picking)`, with `picker_shown = flow.picker is not None`. The HUD is `hud.draw(window, run, flow.best, int(background_ticks))` (HUD-PANEL, replacing `draw_hud(surface, run, below_overlay=debug, best=flow.best)`): the panel and frame are not drawn on `field`, and the debug overlay never needs `below_overlay`. The list: `draw_starfield(surface, run.scroll)`; `render_drifter(surface, obj)` for each `obj` in `run.drifters`, in order (DRA-29); `draw_points_popup(surface, popup)` for each `popup` in `run.popups`, in order (DRA-62); `draw_ship(surface, run.ship)` only if `run.ship_visible`; `draw_graze_ring(surface, ring, run.ship)` for each `ring` in `run.graze_rings`, in order, on every frame whatever `run.ship_visible` is (DRA-117); only if `overlay_visible`, `draw_debug_hitboxes(field, run)` (DRA-29), then `draw_debug_overlay(field, run.ship)`, then `draw_debug_wave_lines(field, run)` (DRA-76); only if `run.game_over`, `draw_game_over(surface)` then `draw_final_score(surface, run.score)` (DRA-61: the final score); then the HUD (above) on the window. Source: systems/ship.md, systems/drifters.md, systems/debug-overlay.md, systems/scroll.md, systems/run.md and systems/hud.md, Presentation; 10-ui.md, rules 1 (the HUD on top) and 3 (the blink); 12-art-and-audio.md, rule 2 (the background stays behind).
- **Drifters behind the ship (DRA-29).** Warnings and meteorites are drawn after the starfield and before the ship, so the player's ship stays on top where they cross.
- **Popups over the drifters (DRA-62).** The points popups are drawn after every drifter, so they show over the other drifters, by Director decision, and before the ship, which stays on top as it does over every drifter. Source: scope report DRA-62, Limits and Decision log (Q5, Director override of Objection 1); systems/run.md, Presentation.
- **Graze rings over the ship (DRA-117).** The rings are drawn right after the ship's place, so they show over the ship they grow from, and under the debug overlay, the Game Over box and the HUD. They don't follow the blink: a ring is not the ship. Graze popups are in `run.popups` and drawn with the coins' popups, in their DRA-62 place. Source: systems/run.md, Presentation (Graze ring); 06-scoring.md, graze_ring.
- **The level-up banner (DRA-148).** Before the first frame, both modes: `level_up_rules, level_up_look = load_level_up(hud_rules)`, right after `load_last_life_rules()`; a bad or missing `level_up.json` raises inside the guard (`systems/level-up/tuning.md`). The first run's waves are `start_waves(book, seed, level_up_rules)`; a run with no waves (the test spawn list) has no banner. Draw order, with `run = flow.run` and `banner = run.level_up`:
  1. On the play area (`_draw_run`): the starfield, then `level_up_view.draw_banner(field, banner)`, then everything `_draw_run` drew before (drifters, popups, ship or burst, graze rings, debug outlines, overlay, wave lines). So the banner is behind everything the player must see.
  2. In `_draw`, right after `_draw_run`: `offset = level_up_view.bump_offset(banner)`; when it is not 0, `field.scroll(0, offset)`. This moves only the play area's picture: the frame, the panel and the HUD are drawn after it and stay still. A game position never reads it. It never follows the ship.
  3. `hud.draw(window, run, best, ticks, level_up=banner)`.
  4. `level_up_view.draw_flight(window, banner)`, right after the HUD and before `hud.dim`, so a paused game dims the flight with everything else.
  The app draws the same on `PLAYING`, `PAUSED` and `GAME_OVER` (the banner is None on game over). It reads `banner` only through `flow.run`; it keeps no copy. No code in the app reads `run.level_up_cue` in this feature: nothing plays. If `Surface.scroll` misbehaves on the play-area subsurface in the browser build, the Integration Engineer reports it and stops: the bump needs a Director decision. Source: `systems/level-up/view.md`, Diagram and Presentation; 10-ui.md, rule 14; 01-vision.md, locked decision 2.
- **Sound** (DRA-158). Before the first frame, both modes: `audio_levels = load_audio_levels()`, right after the level-up values load, then `audio = load_audio(audio_levels)`; a bad or missing `audio.json` or sound file raises inside the guard. Then, once, `audio.start_music()` when `audio` is not None, as the last step before the first frame: the start page holds the game until the player's first click or key press, so the loop starts after it, on the menu. In the tick, right after `step_flow`: `if audio is not None and flow.run_stepped: audio.play_cues(flow.run.sound_cues)`. Only after a tick the flow stepped the run: a paused run, a page and the game-over screen play nothing. Every tick of a frame plays its own cues, even when one frame runs several. The app never reads `level_up_cue`, never stops or restarts the music on its own (only M pauses and resumes it, see Music mute), and never lets sound change a tick, a key or a draw. The mixer and the sounds are `app.audio`'s (`docs/contracts/systems/audio.md`); the tuning file and its checks are `app.audio_tuning`'s. Source: scope report DRA-158, Feature; `docs/contracts/systems/audio.md`, Rules; 15-tech-constraints.md, rule 3; 02-game-flow.md, rule 13.
- **Music mute** (DRA-159). In `_read_events`, on `KEYDOWN` of `pygame.K_m`, when `audio` is not None: `audio.resume_music()` if `audio.music_paused`, else `audio.pause_music()`. On every screen after the start page, with no check of the screen. `KEYUP` of M does nothing. A held key makes no second press: the app never calls `pygame.key.set_repeat`, so a held M gives one `KEYDOWN`, and an M held from the screen before gives none. M never reaches core: it is not in `thrust`, `confirm` or `TickInput`, and it never picks, moves or confirms anything. When `audio` is None, M does nothing. The app keeps no copy of the mute: the state is `audio.music_paused`. The frame loop logs nothing for M: `app.audio` logs `music pause` and `music resume` (`docs/contracts/systems/audio.md`, Logging). M does nothing on the start page because the game does not run before the page's gesture; the press that opens the game never mutes. Source: scope report DRA-159, Feature and Limits; 02-game-flow.md, `mute_key` (locked) and rule 13; 01-vision.md, Locked decision 1.
- **The mute icon** (DRA-159). Before the first frame, both modes: `mute_icon_look = load_mute_icon_look(hud_rules)`, right after `load_audio_levels()`; then, after the display is open, `mute_icon_view = MuteIconView(mute_icon_look, load_mute_icon(mute_icon_look))`, built once and never rebuilt. A bad or missing `mute_icon.json` or picture raises inside the guard (`docs/contracts/systems/mute-icon.md`, Rules, Loading). `_draw` takes two more trailing arguments, `mute_icon_view` and `music_muted`, which the frame loop passes as the view and `audio is not None and audio.music_paused`. In `_draw`, `mute_icon_view.draw(window, music_muted)` is called when `mute_icon_view` is not None, in two places and nowhere else:
  1. On PLAYING, PAUSED and GAME_OVER: right after `level_up_view.draw_flight(window, banner)` and before the `if flow.screen is Screen.PAUSED` branch, so before `hud.dim(window)`. The dim then darkens the icon with the whole window, and the pause box and the game-over box, drawn after the dim, sit over it. On PLAYING nothing follows it.
  2. On MENU, INSTRUCTIONS, LEADERBOARD and CREDITS: right after the page's own draw call (`draw_menu`, `draw_instructions`, `draw_leaderboard` or `draw_credits`), the last call for that screen. Those pages have no dim.
  It is never the last call of `_draw` on a screen with a dim, and it is never drawn on the start page or the error screen. It adds no text and changes no HUD, screen or frame drawing. With `audio` None `music_muted` is False, so nothing shows. Source: scope report DRA-159, Feature; 10-ui.md, `mute_icon_place` and `mute_icon_look`; `docs/contracts/systems/mute-icon.md`, Rules 10, 11 and 13; 91-decision-log.md, row 148.
- **`below_overlay`** is gone (HUD-PANEL). The HUD left the play area, so it can't meet the debug overlay and the flag is gone. Source: 10-ui.md, rule 1.
- `pygame.QUIT`: log INFO `quit` and leave the loop. That only happens on desktop.
- **Arrow keys** (Up, Down, Left, Right): on `KEYDOWN` log DEBUG `key down key=%s x=%.2f y=%.2f`, on `KEYUP` log DEBUG `key up key=%s x=%.2f y=%.2f`, with names `up`, `down`, `left`, `right` and the ship's `x` and `y` (`run.ship.x`, `run.ship.y` from DRA-23) at the moment the event is read (before this frame's ticks). Example: `key down key=up x=320.00 y=240.00`. No other arrow event is logged. From DRA-125 x and y are `flow.run.ship.x` and `.y`, on every screen.
