# Level-up, rationale
Part of: level-up
Read when: you ask why the level-up moment works as it does.

## Rationale
- **A fixed rest, not the end of the last wave (DRA-148).** The Director chose it: the banner plays before the next wave starts, so it never bothers the player. The rest is added where the level rises, in the wave clock, so the wave runner stays the only place that knows when a wave starts.
- **The banner starts on the rise tick, not after the rest gap.** The away log's timeline counts from the tick the level rises, and the cue fires there. With `rest_gap_base` 0 the two readings are the same. If the gap ever grows, the banner plays at the start of the rest and the gap follows it: the rise and the reward stay together.
- **The banner's age lives in the run, as the popups' does.** `PointsPopup` is the precedent: look state that core ages tick by tick, which the view reads. The age is then frozen by pause and by game over for free (the game flow never steps a paused run, and a game-over tick changes nothing), cleared by a new run, and testable without pygame. A view that counted its own frames would drift from the game's ticks and need its own pause logic.
- **The rules ride in the wave state.** `step_waves` needs the rest and the run needs the arrival and life, and both are the same file. `WaveRun` already carries the book to a retry; carrying the rules the same way means `step_run` keeps its signature, `next_run_waves` keeps the rules with no new argument, and a run built without them (every existing test) rests 0 ticks and has no banner.
- **`level_rose` is a flag in the wave state, not a comparison in the run.** The wave clock is the only place that knows why the level changed. A flag set and cleared each call, like `spawns_due`, lets the run start the banner without guessing from two levels, and tells a skipped level from none.
- **`Run.level` stays real; the HUD gets its own shown level.** The level drives the scroll, the spawner, the saves and the debug overlay, and must be true at once (08-difficulty.md, rule 1). Only the HUD delays it, so that the flying number visibly delivers the level. `shown_level` is a core function so the rule has one home and a test can pin it.
- **`HudView.draw` takes the banner as an optional argument, and `HudRun` keeps one level.** The existing fakes in the HUD tests satisfy `HudRun` with only `level`. The app passes `run.level_up` beside `best`, which is also a parameter and not a run field. With no banner or no look, the HUD is the old HUD.
- **The banner stops at once when the last life is lost.** The ship has burst; a reward over a dying run would be wrong, and the HUD must show the level the run reached. The burst is the single fact that marks the last life, so the banner clears when it exists, on the tick it starts and on every last-life tick after.
- **No cue on a last-life rise.** The cue and the banner are one event: no banner, no cue. A jingle over a burst would be the wrong reward.
- **The cue is a property of the run, not an event queue.** One cue exists now. A property true on one state matches how `wave_spawns_due` hands the app a per-tick fact, and the audio feature (AA-03) can decide later whether it wants a general queue. The reader must guard on `run_stepped`, as the drifter hand-off does.
- **Draw order: behind the world, flight over it.** The Director's request and the scope report's Pillar 2 objection meet here: the band, the number and the effects sit just above the starfield, so nothing the player must see is hidden; only the short flight crosses the play area, shrinking, in 0.4 s.
- **The bump moves pixels, not positions.** Locked decision 2 forbids a camera that follows the ship. A fixed offset of the drawn picture, on a timer, tied to the banner's age and not to the ship, is a presentation effect only. The app does it with one scroll of the play area's pixels after the world is drawn and before the HUD, so the frame and the panel stay still.
- **Everything is drawn from images made once.** The Frame-rate check says the rest's empty field already costs 11 to 13 ms of a 16.7 ms frame. So no font render, scale or rotate per frame, no blur, thin shapes as trimmed strips, and the one big shape (the glass) by the cheapest exact blend. The images are built at startup for all 7 levels rather than on the rise tick: a hitch on that tick would be seen by the player at the moment of the reward, and the startup page already waits for loading.
- **The flight ends on the pop's first size.** The flying number ends at the HUD number's size times the pop's start scale, so the swap to the HUD's own number on the arrival tick shows no jump.
- **Its own tuning file.** The look and motion are new numbers the HUD's `hud.json` never had; the Director asked for the HUD's own tuning to stay as it is (away log D7). The three core numbers sit in the same file so the arrival tick the HUD pops on and the flight's end can never disagree.
- **The loader is strict.** The look has no sensible default in code and every value is the Director's to tune. A typo should stop the page with the field named, not silently play with a wrong number.
- **`box_corner_cut` is a tuning value.** The panel's level box has two cut corners baked by the art tool. The flashing outline must follow them or it would draw into the cuts; the tool's size is derived from `panel.scale`, so the value is copied once into the file with a note in the schema. If the art changes, this changes with it.
- **No schema field for the text.** The word LEVEL is a fixed word of the HUD and the banner (10-ui.md, `hud_level`), not a value.
