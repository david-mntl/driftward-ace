## Observations
1. **The glass costs frame rate. Over budget as committed.** With `band.height` 120 and `alpha` 120 the frame rate while the band is open fell from 57 to about 39.5 fps (34% of frames slow), and stayed at about 47 fps through the flight and the pop. With `band.alpha` 0 it stayed at 58.5 to 60 fps. With `band.height` 60 it stayed at 59 to 60 fps. So the cost is the glass area, not the number, ring, streaks, bump, flight or pop. Escape hatches, all tuning values in `game/tuning/level_up.json`: `band.alpha` 0 (no glass, the hairlines stay), `band.height` (60 was nearly free here), `bump.pixels` 0 (not the cost). This is a software-rendered browser in a container; a real desktop browser may be faster, but the project's frame rate is the top open problem (open to-do), and this tuning would put the banner over budget on the same machine class that shows 32 to 40 fps at Wave 4. I did not change any tuning value. The Director or the Architect should pick `band.height` (my suggestion to try: 60, measured above) or a cheaper glass method in `ui/level_up_view.py` (UI Developer).
2. **How soon is the first level rise, and a way to see it faster.** With the real playlists: Wave 0 (1200 px), `w1_fireball` (1320 px + 1 rest tick), `w2_mix` (1000 px) at 1.1 px/tick after a 30-tick start delay. The rise comes at tick 3232, about 54 s after pressing Play (simulated with `core.waves`, then the banner starts and the first wave of Level 2 comes 2.5 s later). There is no existing debug or playtest switch that skips ahead: `tuning/playtest.json` only turns speed and timer scaling off, and `?debug=1` plays the normal waves because `tuning/debug_spawns.json` already says `"play": "waves"`. ## Decisions
- **HUD built after the look is loaded.** `frame-loop.md` lists the HUD first and `load_level_up` after `load_last_life_rules`, but also says the HUD is built with `level_up_look` as its third argument. Both can only hold if the HUD is built after the look. So `load_hud_rules` and the window stay first; the loads run in the contract order; then `load_level_up(hud_rules)`; then `HudView(hud_rules, load_hud_art(hud_rules), level_up_look)` and `LevelUpView(...)`. Source: `systems/app/frame-loop.md`, State and Rules; `systems/level-up/tuning.md`, Interface.
- **`_draw` and `_draw_run` take `level_up_view: LevelUpView | None = None` as the last parameter.** The main session decided this after QA task DRA-148-09 found that a required parameter broke `tests/ui/test_window_view.py` (impact.md promised no existing test would fail). With None: no banner, no bump, no flight, and the HUD gets no banner. The real frame loop always passes the view. Source: main session message; `HudView.draw(level_up=None)` is the same pattern.
- **Table-driven loader.** One table of checks per section, then the records are built by name, so the schema's field names and error wording (`band.alpha must be an integer from 0 to 255`) live in one place. Messages for the cross-rules name the file and the fields. Source: `systems/level-up/tuning.md`, Rules.
- **`level_up_rest` 0 skips only the two core-number rules** (`arrival_tick < banner_ticks` and `banner_ticks <= level_up_rest`), as the contract says the three numbers are then only type-checked. The look rules (pop fits, band order, and so on) still run, because the look is still loaded and drawn code never runs without a banner but a bad file should still be refused. Source: `systems/level-up/tuning.md`, Rules.
- **`level_up_view` is built once before the first frame, in a helper `_build_level_up_view`, using `hud_rules.window.field_x/field_y` as the field origin.** Nothing is built on the rise tick. Source: `systems/level-up/view.md`, Cost.
- **Frame cost measured with `requestAnimationFrame` timestamps, not per-frame logging.** Source: `game/CONTEXT.md`, Logging (log by event).
- **No code reads `run.level_up_cue`.** Nothing plays; the audio feature will hang on it. Source: `systems/level-up/core.md`, The `level_up` cue.
