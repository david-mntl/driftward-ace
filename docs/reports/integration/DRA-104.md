## Decisions
- **UFO loader order:** I check the file's fields, `speed_ratio`, `entry_warning_ticks`, then each weave and band value (`band_top` >= 0, the rest > 0, the ticks ints >= 1). Then the variants, each passing `check_ufo_variant`. Then `default_variant`, then `check_ufo_weave` on the built `UfoTypeExtra`. This is the same shape as `_load_planet`, so a broken value is named before the core rules run. Messages follow app.md: `<file>: variants.<name>: <core message>` and `<file>: <core message>`, each raised `from` the core error. Source: app.md, Rules, Tuning loader (The UFO's file; What the loader builds for the UFO).
- **UFO records:** `VariantTuning(width=float(disc_width), height=float(disc_height), hitbox=ufo_hitbox(...), extra=None)`, and `UfoTypeExtra` with floats for the px values. There is no footprint check, because the dome lies above the disc by design. Source: app.md, What the loader builds for the UFO.
- **Debug row seed:** I check `seed` as an int from 0 to `MAX_SEED`, never a bool. The message mirrors the wave loader's (`rows[i].seed must be an integer from 0 to 4294967295`). A row of a drifter whose class is `seeded` and that gives no seed gets `placement_seed(DEBUG_SPAWNS_SOURCE, i)`. This happens before the load-time spawn, so the kept placement carries the seed and every loop replays the same path. `_row` now takes the row's index; it is a private helper. Source: app.md, Rules, Debug test spawn list (Checks the schema can't express; UFO rows); debug-spawn-list.schema.json, row.seed.
- **No change to the frame or the loop:** UFOs come in through `add_drifters` and are drawn by `render_drifter`, as the DRA-104 Impact table says. The loop stays a fixed 60 Hz accumulator with `await asyncio.sleep(0)` each frame. Source: app.md, DRA-104 Impact; CLAUDE.md, Tech rules.

The headless bad-file cases used a scratch copy of `game/tuning/` in the scratchpad, with `app.tuning.TUNING_DIR` pointed at it. Source: app.md, Integration checks for DRA-104.
